# FRAME — паспорт продукта и архитектуры
Версия паспорта: 2.1.0
Дата: 11.08.2026

## 1. Назначение
FRAME — локальное мобильное PWA для строительного мастера. Главный принцип: минимум визуального шума, максимум полезной полевой информации.

## 2. Сущности
Клиент/контакт → физический объект/адрес → заказ → работы / закрытия / оплаты / расходы / покупки / фото / документы.

Физический объект хранит адрес и заказчика. Заказ является самостоятельным коммерческим объёмом на объекте.

## 3. Полевой прогресс работ
Каждая строка работы хранит:
- согласованное название, количество, единицу и цену;
- текущий progressPct от 0 до 100;
- closedAmount — стоимость этой строки, уже вошедшая в прошлые закрытия.

Быстрый UX:
- тап = 100%;
- долгое нажатие = полный / частичный / сброс;
- частичный прогресс = ползунок с шагом 5%.

`doneAmount = lineTotal × progressPct / 100`
`readyAmount = max(0, doneAmount - closedAmount)`

«К закрытию» заказа = сумма readyAmount всех работ.

## 4. Закрытие объёма
Закрытие — неизменяемый снимок нового выполненного объёма в конкретный момент. Оно хранит номер, дату, сумму, дельту по строкам и document snapshot.

После закрытия:
- текущий progressPct не сбрасывается;
- закрытая сумма добавляется в closedAmount строки;
- «К закрытию» становится 0 для уже зафиксированного объёма;
- дальнейший рост progressPct создаёт только новую дельту.

Исторические закрытия нельзя пересчитывать задним числом. После первого закрытия цена/количество строки блокируются. Для реальной корректировки в будущем нужен отдельный механизм корректировки, а не тихое редактирование истории.

## 5. Документы
КП берёт согласованный состав заказа.
Перечень/акт по закрытию берёт только immutable snapshot конкретного закрытия.
Документ истории хранит closureId, если создан из закрытия.
Изменение дальнейшего прогресса не меняет старый акт или перечень.

## 6. Оплаты
Выполнение и оплата являются разными состояниями.
Платёж может хранить closureId и тем самым быть привязан к конкретному закрытию.
Закрытие показывает: ждёт оплаты / оплачено частично / оплачено.

## 7. Финансовая модель
Стоимость заказа = договорная стоимость работ или сумма строк, если договорный итог не зафиксирован.
Оплачено = фактические платежи.
Осталось = стоимость заказа - платежи.
Чистый доход месяца = фактически получено - невозмещаемые расходы - НПД.
Цель по умолчанию = 300 000 ₽ чистыми за календарный месяц.

Возмещаемые заказчиком покупки показываются отдельно и не уменьшают прибыль по работе. НПД хранится отдельно от статуса выполнения.

## 8. Архангельская, 21 — тест 2.1.0
Для полевого теста добавляется отдельный заказ `workflowKey=arch21-progress-v1` с прогрессом 0%. Состав берётся из согласованного КП и фактических уточнений по объекту.

Контрольный текущий набор должен дать 129 040 ₽ к закрытию, если отметить:
- проём 6 000;
- откосы 13 000;
- черновую электрику 22 040;
- черновую сантехнику 45 000;
- инсталляцию 10 000;
- короб 15 000;
- душевой поддон 60% от 25 000 = 15 000;
- локальный наливной пол 3 000.

## 9. Хранилище и миграции
IndexedDB: FRAME_DB
DB_VERSION: 2
Никаких destructive migration без отдельного решения. Новые поля нормализуются при чтении старых данных. Патч 2.1.0 добавляет тестовый заказ только один раз по ключу `frameWorkflow210DataPatch`.

## 10. Золотые правила UX
1. Не захламлять экран.
2. Главная цифра должна отвечать на практический вопрос мастера.
3. Цифра должна раскрываться до первичных строк.
4. Выполнение и деньги не смешиваются.
5. Исторический документ не меняется задним числом.
6. Длинный список живёт на отдельном экране; bottom-sheet только для короткого выбора.
7. Каждый значимый релиз обновляет код, паспорт, CHANGELOG, ROADMAP и TEST_REPORT.
