# FRAME - паспорт продукта и архитектуры
Версия паспорта: 2.6.0
Дата: 25.08.2026

## 1. Назначение
FRAME - локальное мобильное PWA для строительного мастера. Главный принцип: полезная полевая информация без визуального шума.

## 2. Иерархия данных
Клиент / контакт → физический объект / адрес → заказ → модули работ → работы → закрытия → оплаты / расходы / покупки / фото / документы.

Физический объект является контейнером. Заказ является самостоятельным коммерческим объёмом. Деньги одного заказа не переносятся автоматически в другой заказ того же объекта.

## 3. Модули работ
Работа хранится один раз и имеет `moduleId`. Модуль не создаёт копию работы, а только группирует единые строки для интерфейса и документов.

Базовые модули:
- Демонтаж и проёмы
- Подготовка
- Стены и отделка
- Полы
- Санузел
- Сантехника
- Электрика
- Вентиляция и климат
- Потолки
- Двери и проёмы
- Кухня и мебель
- Прочее

Карточка заказа показывает одну компактную точку входа «Разделы работ». Пустые модули не занимают место. В выборе модулей можно открыть пустой раздел и добавить первую работу.

## 4. Полевой прогресс
Каждая строка работы хранит:
- название;
- исходное количество `qty`;
- единицу `unit`;
- ставку `price`;
- `moduleId`;
- `progressPct` от 0 до 100;
- `closedAmount` - стоимость строки, уже вошедшая в закрытия.

Быстрый UX:
- тап = 100%;
- долгое нажатие = полный / частичный / сброс;
- частичный прогресс = ползунок с шагом 5%.

`doneAmount = lineTotal × progressPct / 100`
`readyAmount = max(0, doneAmount - closedAmount)`

«К закрытию» заказа = сумма `readyAmount` всех строк.

## 5. Закрытие объёма
Закрытие фиксирует только новую дельту выполненного объёма. После закрытия текущий прогресс остаётся, а `closedAmount` увеличивается.

Снимок закрытия хранит физический объём текущей дельты. Например:
- 15,2 м.п. кабеля × 600 ₽;
- 12 шт. подрозетников × 500 ₽;
- 60% комплексной позиции 1 компл. × 25 000 ₽ записывается как 0,6 компл. × 25 000 ₽ = 15 000 ₽.

Последнее закрытие можно отменить только если:
- оно действительно последнее;
- по нему нет платежа с `closureId`;
- по нему нет сохранённого документа с `closureId`.

Если есть оплата или документ, история не переписывается. Для таких случаев нужен отдельный механизм корректировки.

## 6. Документы
КП берёт согласованный состав заказа.
Перечень и акт по закрытию берут frozen snapshot конкретного закрытия.
Снимок содержит реальное количество, единицу, ставку, сумму и пометку прогресса.

Старый документ не пересчитывается при дальнейшем росте прогресса.

Денежные колонки таблицы имеют фиксированную ширину и `nowrap`; название работы может переноситься. Целые рубли печатаются без «,00».

## 7. Оплаты и остаток
`Оплачено` = сумма фактических платежей конкретного заказа.
`Осталось по заказу = max(0, договорная стоимость заказа - оплаты этого заказа)`.

Переплата или округление старого заказа остаётся внутри старого заказа и не уменьшает новый заказ.

Контрольный кейс Леонова 54:
- SPC: договор 33 362,50 ₽, фактически получено 33 363 ₽, закрыт;
- кухня: отдельный заказ 43 000 ₽, при отсутствии платежей остаток 43 000 ₽.

## 8. Возмещаемые покупки
Возмещаемые заказчиком покупки не являются оплатой работ и не уменьшают прибыль по работе.

Показатель «К возмещению» кликабелен и ведёт прямо к покупкам соответствующего заказа. На уровне объекта он сначала показывает заказы с невозмещёнными покупками.

## 10. Хранилище и миграции
IndexedDB: `FRAME_DB`
DB_VERSION: `2`

Разрушающей миграции нет. Новые поля нормализуются при чтении старых данных.
Миграционный ключ 2.1.0 сохраняется для совместимости.
Патч 2.2.0 выполняется один раз по ключу `frameWorkflow220DataPatch`.

## 11. Золотые правила UX
1. Не захламлять экран.
2. Объект и заказ не смешивать: объект - место, заказ - коммерческая история.
3. Главная цифра должна отвечать на практический вопрос мастера.
4. Цифра, требующая действия, должна вести прямо к первичным строкам.
5. Выполнение, закрытие, оплата и возмещение являются разными слоями.
6. Исторический документ не меняется задним числом.
7. Длинный список живёт на отдельном экране; bottom-sheet используется для короткого выбора.
8. Каждый значимый релиз обновляет код, паспорт, CHANGELOG, ROADMAP и TEST_REPORT.

## 13. FRAME AI · слой разговорного управления · 2.4.0

### Принцип
AI не является хранилищем данных. Источник истины — структурированная база FRAME. AI является интерфейсом между естественной речью пользователя и операциями над базой.

Целевой цикл:
`речь / текст → понимание намерения → структурированное действие → предпросмотр → запись в FRAME_DB → журнал изменения`.

### Beta 2.4.0
Первый слой выполняет локальный разбор ограниченного набора команд без внешнего LLM:
- `payment` — фактическая оплата;
- `expense` — невозмещаемый расход / комиссия;
- `purchase` — покупка мастера;
- `work_add` — новая работа;
- `work_complete` — прогресс существующей работы 100%;
- `order_note` — заметка к заказу.

Перед применением пользователь видит целевой заказ и интерпретацию. В Beta автоматическая запись без подтверждения запрещена.

### Контекст
Если AI открыт из карточки заказа, этот заказ становится текущей целью. Если AI открыт с главной, используется выбранный активный заказ. Фраза может подсказать другой объект по адресу/имени, но результат всегда показывается в предпросмотре.

### Голос
При наличии `SpeechRecognition` / `webkitSpeechRecognition` FRAME может заполнить поле распознанной речью. Голос не является отдельным источником истины: после распознавания он превращается в тот же текстовый запрос.

### Журнал и откат
`frameAiLogV240` хранит последние AI-операции: исходную фразу, тип, цель, время, краткое описание и минимальные данные для отката. Поддерживается отмена последнего неотменённого AI-действия. Журнал входит в backup 2.4.0.

### Следующий архитектурный шаг
Настоящий LLM подключать только через безопасный backend. Никогда не хранить секретный API-ключ в PWA/JavaScript клиента.

LLM должен возвращать валидируемый структурированный результат, например:
`{ action, objectId, orderId, payload, confidence, needsConfirmation }`.

FRAME самостоятельно валидирует действие и применяет его к базе. Модель не получает прямой произвольный доступ к IndexedDB.

### Будущие возможности
- несколько действий из одной фразы;
- вопрос к базе: «сколько мне должны?»;
- поиск объекта без ручного выбора;
- фото + голос при первичном осмотре;
- разбор чеков и привязка к объекту;
- создание КП из разговора;
- умное уточнение только при реальной неоднозначности;
- высокий confidence → опциональное применение без лишнего подтверждения;
- общий AI-core для будущих FRAME Renovation / Marine / Service.


## 14. FRAME 2.5.0 · AI Brain Bridge

### Архитектурный переход
Локальный regex-парсер 2.4.x остаётся только как ограниченный fallback для простых команд. Основной целевой путь теперь:
`речь → текст в FRAME → FRAME AI Server → LLM → structured actions → предпросмотр → подтверждение → FRAME_DB`.

### AI provider abstraction
FRAME не должен зависеть от конкретной модели. Клиент обращается к одному endpoint `/analyze`. Текущий provider — локальная LLM через Ollama на ноутбуке. Сервер уже имеет сменный provider-слой для будущего OpenAI Responses API без переписывания PWA и базы.

### Что отправляется в AI Brain
PWA отправляет:
- исходную текстовую фразу;
- текущий выбранный target как подсказку;
- компактный контекст: object/order/work IDs, адреса, имена клиентов, статусы, суммы заказов, оплаты и строки работ.

Полные фото и документы в 2.5.0 в AI Brain не отправляются. Источник истины остаётся на устройстве в `FRAME_DB`.

### Белый список AI-действий
LLM может предложить только структурированные действия:
- `create_object`;
- `create_order`;
- `update_object`;
- `update_order`;
- `add_work`;
- `delete_work`;
- `update_work`;
- `set_work_progress`;
- `add_payment`;
- `add_expense`;
- `add_purchase`;
- `add_note`.

Модель не получает прямого доступа к IndexedDB и не выполняет произвольный JavaScript. Применяет изменения только код FRAME после валидации и предпросмотра.

### Новые объекты
Ключевой regression-кейс 2.5.0: фраза «Новый объект: Владивосток, Октябрьская 16, кв. 28, заказчик Екатерина, монтаж кухни 50 тысяч» не должна попадать в текущий объект Архангельская/Леонова. AI обязан вернуть `create_object` + `add_work` с временными ссылками `@new_object_*` / `@new_order_*`.

### Безопасность
- адрес AI Server и локальный access token хранятся только в localStorage устройства;
- access token не вшивается в GitHub Pages и не входит в исходный релиз;
- сервер по умолчанию слушает `127.0.0.1`;
- внешний доступ предполагается через HTTPS tunnel;
- CORS ограничен origin `https://frame-vl.github.io`;
- удаление работы требует отдельного подтверждения в UI;
- неоднозначные destructive-команды должны возвращать clarification вместо действия.

### Undo 2.5.0
Для пакетных AI Brain-команд журнал хранит обратные операции, а не полные снимки объектов с фотографиями. Это позволяет отменять создание объекта/заказа, добавление/удаление/изменение работы, оплаты, расходы, покупки, заметки и прогресс без раздувания localStorage фотографиями.

### Совместимость
- IndexedDB: `FRAME_DB`;
- DB_VERSION: `2`;
- разрушающей миграции нет;
- данные 2.3/2.4 сохраняются;
- AI log key сохраняется `frameAiLogV240` для обратной совместимости.


## 15. FRAME 2.5.2 · AI Brain Network Hotfix

## 20. AI reliability guard 2.6.0
Если внешний AI Brain возвращает уточнение или отказывается от очевидной поддерживаемой команды, FRAME пробует детерминированный локальный разбор. Это страховка для простых действий (например, заметка, оплата, покупка, завершение работы), а не замена LLM. Простые команды не должны зависеть от вариативности небольшой локальной модели.
